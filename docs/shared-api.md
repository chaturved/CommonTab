# Shared expense API

Base path: `/v1`. Everyone in a group is a **member**: a person with a name who may or may not have an account. Member ids (not account ids) are what expenses, splits, balances and payments refer to. The OpenAPI schema is available at `/openapi.json`. Protected routes accept `Authorization: Bearer <accessToken>` (native apps) or the httpOnly session cookie `commontab_session` (the web app; the browser sends it, script cannot read it). A write that authenticates by cookie must also send the header `X-CommonTab-Client: 1` (CSRF protection); bearer requests do not need it. The header wins if both are present. Request and response JSON use camel case for shared expense fields. All money is an integer count of the group's minor currency unit: USD 1250 represents $12.50; JPY 1250 represents ¥1,250.

## Accounts and groups

- `POST /accounts` with `{email,name,password}` creates an account and returns `{accessToken,expiresAt,user}`. Passwords must be at least 15 characters.
- `POST /auth/password-reset` with `{email}` always returns `202` with `{}`, whether or not the email has an account (nothing reveals which). If it does, an email with a short reset code (like `ABCD-2345`, valid one hour) is sent after the response; asking again within a minute sends nothing new, and a new code replaces the earlier ones. `POST /auth/password-reset/confirm` with `{email, code, newPassword}` (15 to 128 characters; the code may be typed in any case, with or without the dash) returns `204` and sets the password and signs the account out everywhere; a wrong, expired or used code returns `400` (`code: "invalid_code"`). Five wrong guesses burn the code. Both routes share the strict per-IP limit of sign-in.
- `PATCH /me` with `{name}` renames the account. `POST /me/password` with `{currentPassword, newPassword}` (15 to 128 characters) returns `204`, sets the password and signs every other session out (this one stays). A wrong current password is `403` with `code: "wrong_password"`, never `401`, so a client does not mistake it for an ended session. `POST /me/delete` with `{password}` returns `204`, clears the cookie and deletes the account: its sign-ins and reset codes go, groups where nobody else has an account are deleted with their expenses and payments, and in shared groups the person stays under their name with no account (`userID: null`, `email: null`) so nobody's balance changes; if they owned the group it passes to the longest-standing other account. Both routes share the strict per-IP limit of sign-in.
- **Leaving and ending groups (migration `0007`).** `POST /groups/{id}/leave` returns `204` and the person is marked removed; while their balance is not zero it is `409` (`code: "owes_balance"`, `balanceMinor`: positive when owed, negative when owing). The owner leaving hands the group to the longest-standing other account, and with no other account it is `409` (`last_account`). `DELETE /groups/{id}/members/{memberId}` (owner only, `403 not_owner`) removes a person even while they owe; their balance stays in the group, `409 use_leave` for yourself. `POST /groups/{id}/archive` (any member, `409 not_settled` unless everyone is even) and `POST /groups/{id}/unarchive`; saving an expense in an archived group brings it back. `DELETE /groups/{id}` (owner only, `409 not_settled`) soft-deletes the group. A removed or left account gets `404` on that group from then on (read and write). `GET /groups` returns, besides the snapshots of groups you can use, a stub `{id, name, status: "removed" | "deleted", since}` for each group you lost access to, so the app can keep its last copy read-only. Snapshots now carry `archived` and each member carries `removedAt` (`null` while they are in the group). Removed people still count in balances and stay in the member list.
- **Activity feed (migration `0008`).** `GET /activity?since=<seq>&limit=<1..500, default 200>` returns `{events, next}` for the groups you can use, oldest first. An event is `{seq, groupID, actorID, kind, subjectID, data, at}`; `seq` only grows, so a client keeps the last `next` and asks for what comes after it. `actorID` is a member id (null when unknown). Kinds and their `data`: `group.created` `{name}`; `expense.added` `{merchant, amountMinor}`; `expense.edited` `{merchant, amountMinor, previousMerchant, previousAmountMinor}`; `expense.deleted` `{merchant, amountMinor}`; `payment.recorded` `{fromID, toID, amountMinor}` (`subjectID` is the payment); `member.joined` and `member.left` `{}`; `member.added` and `member.removed` `{name}`; `group.archived` and `group.unarchived` `{}`. `subjectID` is the expense, payment, member or group the event is about. A write that changes nothing (a retry of the same request) records no event. Events from before this existed are not backfilled.
- `POST /auth/sessions` with `{email,password}` returns the same session shape. Sign-up and sign-in also set the session cookie (`HttpOnly; Secure; SameSite=Lax`, 30 days; `COOKIE_SECURE=false` for local http). `DELETE /auth/sessions` revokes the current token and clears the cookie. Tokens expire after 30 days.
- `GET /me` returns the current account; `PATCH /me` changes its name.
- `GET /healthz` (no login) returns `{"status":"ok"}` when the API can reach its database and `503 {"status":"unavailable"}` when it cannot, so the app can tell "server down" from "no connection". `/health` is an older alias.
- `GET /groups` returns complete group snapshots for the signed-in account. `GET /groups/{groupId}` returns its current snapshot. `PATCH /groups/{groupId}` changes its name.
- A snapshot lists `members`: `{id, name, userID, email}`. `userID` and `email` are `null` for a person without an account. `meMemberID` is the member linked to the signed-in account (the app's "me"), and `ownerID` is the owner's member id.
- `POST /groups` with `{name, currencyCode}` creates a group with the creator as its only member (`201`). Optional fields support uploading a group that already exists on a phone: `id` (a client UUID), `members: [{id, name}]` and `meMemberID` (which of those people is the signed-in account; required with `members`, up to 50 people). Repeating the same request returns `200` with the existing group and creates nothing; the same `id` with a different body, or an id that belongs to someone else's group, returns `409` (`code: "id_conflict"`). A member id already used elsewhere also returns `409` and nothing is created.
- `PUT /groups/{groupId}/members/{memberId}` with `{name}` adds a person without an account, or renames one. The client chooses `memberId`, so repeating a request is safe; any member of the group may call it, names need not be unique, and the last write wins. Returns `200` with the member; the same id in another group returns `409`.
- `POST /groups/{groupId}/invitations` with `{email, memberID?}` returns a private seven-day code. With `memberID` (an existing person who has no account), accepting the invitation links that person to the accepting account, so their past expenses and balance become the account's; without it, accepting adds a new member named after the account. `POST /invitations/accept` with `{inviteToken}` joins only if the signed-in account has that email, and returns `409` if the account is already in the group or the person was linked in the meantime. `POST /groups/{groupId}/invite-code` with `{memberID?}` (any member) returns `{code, expiresAt, groupID, memberID}` with `201`: a short code like `ABCD-2345` (8 characters, no I, L, O or U), valid seven days, not tied to an email. A code for the whole group can be used by many accounts; a code with `memberID` links that person to the first account that uses it, then stops working. `DELETE /groups/{groupId}/invite-code` (any member) ends every open code for the group and returns `204`; make a new one with the `POST` above. `POST /invitations/join` with `{code}` (the code may be typed in any case, with or without the dash or spaces) adds the signed-in account to the group and returns the group snapshot (`200`); joining a group you are already in also returns `200` with the group. An unknown, expired, used-up or malformed code returns `404`; a person linked in the meantime returns `409` (`code: "id_conflict"`). Joining is rate limited per IP like sign-in. The application displays the email code for private sharing; it does not send email.

## Expenses

`PUT /groups/{groupId}/expenses/{expenseId}` creates or replaces one expense. `payerID` and `participants` are member ids of that group:

```json
{
  "id": "00000000-0000-0000-0000-000000000001",
  "merchant": "Groceries",
  "occurredAt": "2026-09-30T12:00:00Z",
  "category": "groceries",
  "notes": "",
  "amountMinor": 10001,
  "payerID": "00000000-0000-0000-0000-000000000002",
  "method": "equal",
  "participants": ["00000000-0000-0000-0000-000000000002"],
  "values": [],
  "version": null
}
```

For `exact`, `values` contains one string per participant with integer **minor units**, and its sum must equal `amountMinor`. For `percentage`, the values are decimal percentage strings totaling exactly 100. Equal splits divide whole minor units; remaining units go to participants in request order. Percentage splits use largest remainders with request order breaking ties. The response contains canonical `allocations`, the original `values`, and an incremented `version`. Create with `version: null`; edit with the last version received. A stale or conflicting write returns `409` (see Conflicts and retries).

`DELETE /groups/{groupId}/expenses/{expenseId}` returns `204`. It marks the expense deleted instead of removing it (a *tombstone*) and bumps its version. Delete wins: it succeeds whatever version the caller last saw (`?version=N` is still accepted and ignored), repeating it is a no-op, and deleting an id the server has never seen is also a no-op. Group snapshots return `members`, `expenses` (live only), `deletedExpenses` (tombstones, each a full expense with `deletedAt` set), `settlements`, `balances`, and the group `version`. Balances ignore tombstones. Live expenses have `deletedAt: null`. Every expense record (live, tombstone, or the `current` in a `409`) carries `updatedAt`, the UTC time of its last change on the server; clients use it to decide whose edit is newest. A positive balance means that member is owed money; a negative balance means they owe money. The sum of balances is zero.

## Settlements and receipts

`POST /groups/{groupId}/settlements` accepts `{id,fromID,toID,amountMinor}` and returns `201` with the settlement. `fromID` and `toID` are member ids. The signed-in account must be linked to one of the two. The payer must have a negative balance, the recipient a positive balance, and the amount cannot exceed either outstanding side. These checks run against the balances at the moment the request is applied, never against a group version, so a payment queued offline does not go stale (`groupVersion` is accepted and ignored for older clients). Repeating a request with the same `id` and the same payment returns `200` with the stored settlement and changes nothing; the same `id` with a different payment returns `409` (`code: "id_conflict"`). An amount above what is owed returns `422` with `code: "exceeds_balance"` and `maxAmountMinor`, the most that can be paid (`0` when nothing is owed in that direction).

`PUT /groups/{groupId}/expenses/{expenseId}/receipt` uploads raw JPEG or PNG bytes with the matching `Content-Type`. `GET` returns the image only to group members, and `DELETE` removes it. The 5 MB limit applies to uploads. The server decodes, caps image dimensions, and stores a normalized JPEG without source metadata. Receipt content is excluded from analytics.

## Conflicts and retries

Every write carries a client-generated id, so retrying after a lost response cannot duplicate or conflict with itself:

- `PUT` of an expense whose content equals what the server already stores returns `200` with the stored record (no new version), whatever `version` it carries.
- A `PUT` with different content and a stale `version` (or `version: null` for an id that exists) returns `409`.
- A `PUT` on a deleted expense returns `409` unless its `version` equals the tombstone's version, which **restores** the expense (`deletedAt` becomes `null`, version +1). A replayed create therefore never resurrects a deleted expense.
- Newest edit wins: the client keeps the loser as history and resolves from the `current` record in the `409` body.

## Error behavior

Errors are `{"detail": "..."}`, plus `code` and extra fields where listed. Protected resources return `401` for missing or expired account sessions and `404` when the account is not a member, without revealing whether a group exists. Invalid input returns `422`. Conflicting versions or duplicate identifiers return `409`; expense conflicts add `code: "version_conflict"` and `current`, the server's current record (a tombstone if it was deleted). Other codes: `id_conflict`, `not_found`, `exceeds_balance`, `rate_limited`.

Rate limits: sign-up and sign-in are limited per IP (default 10 a minute), everything else per session (default 600 a minute). Over the limit returns `429` with a `Retry-After` header and `retryAfterSeconds`. Clients treat `429` like a network failure and back off. `/healthz` is never limited.
